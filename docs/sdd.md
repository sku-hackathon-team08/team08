# SDD — 명세 기반 개발

> 상태: 세부 개발 흐름은 검토안입니다. 작업 목록은 GitHub Issues, 병합은 Squash merge로 관리합니다.

SDD(Spec-Driven Development)는 요구사항·계약에 적힌 기대 동작을 구현과 검증으로 연결하는 개발 방식입니다.
기준 문서는 [SOT](sot.md)에서 찾고, 이 문서에서는 작업 흐름을 관리합니다.

## 잠정 작업 흐름

1. **작업 확인:** GitHub 이슈에서 목적·범위·담당자·완료 조건을 확인하고 작업 브랜치를 연결합니다.
2. **명세 확인:** PRD와 해당 기능·기술 명세에서 목표·범위·인수 조건·미결정 사항을 확인합니다.
3. **명세 보완:** 새로운 요구나 계약 변경은 해당 기준 문서에 작성하고 검토 상태와 영향을 표시합니다.
4. **구현:** 작업 범위에 맞게 `frontend/`와 `backend/` 코드를 작성합니다.
5. **검증:** 인수 조건과 기술 계약을 기준으로 검사하고 실행 결과·미실행 항목·남은 차이를 기록합니다.
6. **PR 검토·병합:** 관련 이슈·명세·검증 결과를 PR 템플릿으로 공유하고, 리뷰 후 스쿼시 머지합니다. 이슈 완료 조건을 확인해 종료하거나 남은 작업을 갱신합니다.

작업 규모에 맞게 흐름을 조정할 수 있습니다. 각 단계마다 별도의 승인을 요구하는 절차는 아닙니다.
사용자의 명시적 지시를 우선하며, 검토안과 다르다는 이유로 추가 승인이나 작업 중단을 요구하지 않습니다.

## 단계별 가이드

- 구현: [개발 컨벤션](guides/development.md)
- 검증·TDD: [테스트 가이드](guides/testing.md). 핵심 로직은 실패하는 테스트 → 최소 구현 → 리팩터링을 우선 고려합니다.
- 이슈·브랜치·커밋·PR: [Git 협업](guides/git-workflow.md)

세부 항목의 적용 상태는 [가이드 목차](guides/index.md)에서 확인합니다.

## 기록 위치

- 제품·기능·API·DB·외부 연동의 기준: [SOT가 연결하는 문서](sot.md)
- 중요한 기술 선택과 이유: [결정 기록](decisions.md)
- 작업 목록·담당자·진행·막힘·완료 조건: GitHub 이슈. 상태는 [Git 가이드의 라벨 기준](guides/git-workflow.md#단순-라벨-구성)으로 관리
- 구현·검증 결과: 이슈에 연결된 PR
- 긴 작업의 계획: 필요할 때 `docs/plans/<작업명>.md`를 만들고 목표·단계·진행·검증·남은 일을 기록

문서형 계획을 작성하면 이슈에서 링크하고, 진행 상태는 이슈를 기준으로 갱신합니다.
이슈·계획·PR 설명에 계약의 별도 원본을 만들지 않습니다. 명세의 확정과 구현 완료는 각각 구분합니다.

## 추후 결정

- 기술 스택에 맞는 검증 명령과 CI
- PR 필수 리뷰 수와 세부 검토 기준
