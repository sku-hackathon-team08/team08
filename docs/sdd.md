# SDD — 명세 기반 개발

> 상태: 검토안. 팀의 세부 작업 절차는 아직 확정하지 않았습니다.

SDD(Spec-Driven Development)는 요구사항·계약에 적힌 기대 동작을 구현과 검증으로 연결하는 개발 방식입니다.
기준 문서는 [SOT](sot.md)에서 찾고, 이 문서에서는 작업 흐름을 관리합니다.

## 잠정 작업 흐름

1. **명세 확인:** PRD와 해당 기능·기술 명세에서 목표·범위·인수 조건·미결정 사항을 확인합니다.
2. **명세 보완:** 새로운 요구나 계약 변경은 해당 기준 문서에 작성하고 검토 상태와 영향을 표시합니다.
3. **구현:** 작업 범위에 맞게 `frontend/`와 `backend/` 코드를 작성합니다.
4. **검증:** 인수 조건과 기술 계약을 기준으로 검사하고 실행 결과·미실행 항목·남은 차이를 기록합니다.
5. **PR 검토:** 관련 명세·변경 이유·검증 결과를 연결해 PR로 공유합니다.

작업 규모에 맞게 흐름을 조정할 수 있습니다. 각 단계마다 별도의 승인을 요구하는 절차는 아닙니다.
사용자의 명시적 지시를 우선하며, 검토안과 다르다는 이유로 추가 승인이나 작업 중단을 요구하지 않습니다.

## 기록 위치

- 제품·기능·API·데이터의 기준: [SOT가 연결하는 문서](sot.md)
- 중요한 기술 선택과 이유: [결정 기록](decisions.md)
- 구현·검증 결과: 해당 PR
- 긴 작업의 계획: 필요할 때 `docs/plans/<작업명>.md`를 만들고 목표·단계·진행·검증·남은 일을 기록

계획이나 PR 설명에 계약의 별도 원본을 만들지 않습니다. 명세의 확정과 구현 완료는 각각 구분합니다.

## 추후 결정

- 기능별 명세의 상세 양식
- 기술 스택에 맞는 검증 명령과 CI
- PR 리뷰와 병합 방식
