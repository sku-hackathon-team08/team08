# API 문서

프론트·백엔드가 함께 참고하는 API 계약의 시작점입니다. 기능별 문서는 이 폴더에 작성합니다.

[해커톤 백엔드 API](hackathon.md)가 현재 채택·구현 계약입니다. 세션·분석·신고·담당·지원·통계·PDF와 공통 입력 오류를 구현했습니다. [축제 서비스 API v0.1](festival.md)은 이전 검토안 보존 자료입니다. 행사 신청·발급과 GPS·구역 판정·접근 경로는 사용자 결정으로 이번 범위에서 제외합니다.

## 문서별 책임과 기능별 명세 위치

- 공통 계약은 이 폴더의 주제별 문서에서 관리합니다. `errors.md`는 공통 오류, `naming.md`는 필드 네이밍의 기준입니다.
- 기능별 API 명세는 `docs/api/<기능명>.md`에 작성하고 위 API 목록에 등록합니다. 예를 들어 사용자 기능이 정해지면 `users.md`를 추가합니다.
- 기능별 명세에는 메서드·경로, 인증·권한, 요청 필드·예시, 성공 응답·상태, 오류 코드·발생 조건, 인수 조건을 적습니다.
- 오류 JSON 구조는 `errors.md`를 참조하고, 개별 명세에는 해당 API에서 발생하는 상태·코드·조건을 기록합니다. 예를 들어 `409 / DUPLICATE_NAME / 이름 중복`처럼 적되 실제 코드와 조건은 기능별로 결정합니다.
- 한 기능의 명세가 길어지면 `docs/api/<기능명>/index.md`와 작업별 문서로 나눕니다. 예를 들어 `chatrooms/index.md`, `chatrooms/create.md` 형태로 구성하고 기존 링크도 갱신합니다.
- 위 기능명은 배치 예시입니다. 서비스가 미정인 동안 예시 파일·폴더를 미리 만들지 않습니다.
- `integration-contracts.md`는 미정 항목의 검토 목록입니다. 합의한 본문은 공통 계약 또는 기능별 명세로 옮기고, 완료된 항목은 검토 목록에서 제거하거나 확정 문서 링크만 남깁니다.
- 스키마의 이름·분리·생성·변환·검증 책임은 [백엔드 스키마 작성 가이드](../guides/backend.md#스키마-작성-패턴)를 참고합니다. 실제 요청·응답 필드와 입력 정책은 해당 API 계약에서 정합니다.
- 레이어별 구현 책임·예외 핸들러 연결 방법은 [백엔드 개발 가이드](../guides/backend.md#오류-처리-구현과-연동)에서 관리합니다. API 명세에는 외부에서 관찰할 계약과 검증 조건을 기록합니다.

## 문서 작성 기준

- 기능별 문서에 상태, 메서드·경로, 목적, 인증 여부, 요청·응답 예시, 오류·제약을 적습니다.
- 구현 전 계약을 먼저 합의하고, 미구현 항목은 상태에 표시합니다. 프론트는 필요한 기능 문서부터 확인합니다.
- API 변경 시 이 문서의 계약·백엔드 구현·프론트 호출부·테스트를 함께 확인합니다.
- `docs/api/`는 합의한 계약과 사용 맥락, FastAPI의 `/openapi.json`·`/docs`는 현재 구현된 스키마와 호출 확인을 담당합니다.
- 계약과 OpenAPI가 다르면 어느 쪽이 바뀌어야 하는지 확인합니다. 자동 생성된 스키마가 합의한 계약을 자동으로 대체하지 않습니다.
- 공통 오류는 [오류 계약](errors.md)에 기본 형식과 공통 코드 5개를 확정했으며 400·404·405·500을 구현했습니다. 422 필드 검증과 서비스 API의 중복 입력 검출도 구현했습니다. 필드 네이밍은 [네이밍 계약](naming.md)을 따릅니다. 인증·멱등성·버전·응답 표현의 현재 채택 범위는 [해커톤 계약](hackathon.md)이 기준입니다. 설명용 예시를 구현된 기능이나 확정 코드 목록으로 취급하지 않습니다.

저장 모델·ERD·제약은 [DB 명세](../db/index.md), 백엔드와 외부 제공자 사이의 통신은 [외부 연동 명세](../integrations/index.md)에서 관리합니다. 프론트가 사용하는 인증·오류·스트리밍 계약은 이 API 문서에 둡니다. 문서 책임은 [SOT](../sot.md)를 참고합니다.
