# 공통 오류 응답

> 상태: 기본 응답 형식·공통 오류 코드 5개 확정. 400·404·405·500의 일반 오류 스키마·핸들러·OpenAPI·테스트를 구현했습니다. 422는 현재 FastAPI 기본 응답을 유지하며 공통 형식은 미적용입니다. 필드 오류의 세부 표현과 변환 핸들러는 첫 기능 개발 시 결정·구현합니다.

[API 목차](index.md) · [추가 계약 검토](integration-contracts.md)

## 합의한 기본 형식

본문을 제공하는 앱의 HTTP 오류는 적절한 4xx·5xx 상태 코드와 `application/json`으로 응답합니다.
성공을 뜻하는 200으로 오류를 감싸지 않습니다. 팀 자체 계약이며 RFC 9457 준수 형식으로 표시하지 않습니다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `status` | 정수 | 실제 HTTP 응답 상태 코드와 일치 |
| `code` | 문자열 | 프론트가 분기하는 안정적인 오류 식별자 |
| `detail` | 문자열 | 사용자에게 보여줄 수 있는 설명. 내부 예외·SQL·비밀 값은 포함하지 않음 |
| `errors` | 배열 | 필드별 입력 오류. 없으면 생략하거나 null로 보내지 않고 `[]` |

아래는 형식 예시입니다. 중복 이름 기능이나 해당 업무 코드를 구현했다는 뜻이 아닙니다.

```http
HTTP/1.1 409 Conflict
Content-Type: application/json
```

```json
{
  "status": 409,
  "code": "DUPLICATE_NAME",
  "detail": "이미 사용 중인 이름입니다.",
  "errors": []
}
```

오류 코드는 `UPPER_SNAKE_CASE`를 사용하고 의미를 유지합니다. 설명 문구를 바꿔도 코드는 바꾸지 않습니다.
기능별 문서에서 실제로 필요한 코드·상태·발생 조건을 정의하며, 예상하는 업무 오류를 미리 대량 등록하지 않습니다.

## 공통 오류 코드

아래는 응답 최상위 `code`의 확정 목록입니다. 상태 코드와 발생 조건을 함께 사용합니다.

| HTTP 상태 | code | 발생 조건 |
|---|---|---|
| 400 | `BAD_REQUEST` | 요청 형식·구성 문제를 앱에서 명시적으로 400으로 거절하는 경우 |
| 422 | `VALIDATION_ERROR` | 요청의 필수값 누락·타입·길이 등 입력 검증 실패 |
| 404 | `NOT_FOUND` | 요청한 경로나 대상이 없음 |
| 405 | `METHOD_NOT_ALLOWED` | 해당 경로에서 지원하지 않는 HTTP 메서드 |
| 500 | `INTERNAL_SERVER_ERROR` | 예상하지 못한 서버 오류 |

- FastAPI의 기본 요청 검증 실패는 422로 유지합니다. JSON 파싱 등 요청 검증 오류를 형식 문제라는 이유만으로 일괄 400으로 바꾸지 않습니다.
- 422는 클라이언트의 요청 입력에 대한 코드입니다. 서버 응답 스키마 검증 실패는 서버 오류로 처리합니다.
- `detail`은 상황에 맞는 안전한 안내 문구이며 코드별 고정 문구가 아닙니다. 프론트는 문구가 아니라 `code`로 분기합니다.
- 필드별 오류가 없는 경우 `errors`는 `[]`입니다. 입력 오류 항목의 구조는 아래 검토안으로 남겨둡니다.
- 이 목록은 모든 HTTP 오류를 5개로 강제 변환하는 표가 아닙니다. 인증·권한·요청 제한과 업무별 오류는 해당 기능 도입 시 필요한 상태와 코드를 추가합니다.
- 같은 HTTP 상태에서도 프론트가 구별할 필요가 있는 업무 오류는 기능별 명세에 별도 코드를 정의할 수 있습니다. 앞의 `DUPLICATE_NAME`은 아직 미확정 예시입니다.

아래는 현재 핸들러가 반환하는 서버 오류 응답입니다.

```json
{
  "status": 500,
  "code": "INTERNAL_SERVER_ERROR",
  "detail": "요청 처리 중 오류가 발생했습니다. 잠시 후 다시 시도해주세요.",
  "errors": []
}
```

## 입력 검증 오류

> 구현 상태: 이 절은 합의한 목표 형식과 남은 검토안입니다. 현재 요청 검증 실패는 FastAPI 기본 422 응답으로 반환하며, 아래 공통 형식으로 변환하지 않습니다.

요청의 입력 검증 실패는 422로 응답하고, 확인 가능한 필드 오류를 함께 반환합니다.
일반 설명은 `detail`, 개별 오류는 `errors`에 두어 `detail`의 타입이 배열이나 객체로 바뀌지 않게 합니다.
필드명은 Python 내부 이름이 아니라 프론트가 요청에 사용하는 JSON 이름과 맞춥니다.

아래는 **필드 오류 항목의 검토안**입니다. 최상위 `VALIDATION_ERROR`는 확정 코드입니다. `errors` 내부의 `field` 표현·`REQUIRED` 코드는 미확정이며, `displayName`은 설명용 필드입니다.

```json
{
  "status": 422,
  "code": "VALIDATION_ERROR",
  "detail": "입력값을 확인해주세요.",
  "errors": [
    {
      "field": "displayName",
      "code": "REQUIRED",
      "detail": "이름을 입력해주세요."
    }
  ]
}
```

필드 항목의 `code`·`detail`은 문자열로 두는 안을 권장합니다. 같은 필드의 오류가 여러 개일 수 있으므로 프론트는 첫 메시지를 표시하거나 목록으로 다룰 수 있습니다.
중첩 객체·배열 경로, body·query·path 구분, 특정 필드를 가리킬 수 없는 오류의 표현은 미정입니다. 현재 결정을 보류하며, 첫 입력 폼·기능 API 개발 시 실제 요청을 기준으로 [추가 계약 검토](integration-contracts.md)에서 합의합니다. 필드 오류를 변환하는 검증 핸들러도 그 이후 구현합니다.
Pydantic의 원본 오류 목록을 그대로 응답하지 않고 공개 필드만 골라 변환합니다. 검증 라이브러리의 내부 코드·입력 원문을 공개 계약으로 사용하지 않습니다.

## 적용 범위

현재 구현은 명시적인 HTTP 400·404·405·500과 예상하지 못한 서버 오류에 공통 형식을 적용합니다. 미등록 경로의 404·지원하지 않는 메서드의 405를 포함합니다. 서버 응답 스키마 검증 실패도 안전한 500으로 처리하며 요청 입력의 422로 바꾸지 않습니다.

명시적인 HTTP 400·404·405의 문자열 `detail`은 공개 안내로 사용하므로 작성자가 안전한 문구만 넣습니다. 배열·객체 등 문자열이 아닌 설명은 상태에 맞는 일반 문구로 대체합니다. HTTP 500의 설명과 예상하지 못한 예외 내용은 항상 위 서버 오류 안내로 대체합니다.

401·403·409·429·503 등 아직 공통 코드가 정의되지 않은 상태와 명시적인 HTTP 422는 FastAPI 기본 HTTP 오류 처리에 위임합니다. 상태에 맞지 않는 공통 코드를 붙이지 않으며, 이 응답에 공통 JSON 형식을 보장하지 않습니다. 요청 검증 실패의 기본 422도 그대로 유지합니다.

앱이 생성하는 404·405도 포함해 형식을 맞추고, 필요한 `WWW-Authenticate`·`Retry-After`·`Allow` 헤더를 유지합니다.
예상하지 못한 500 오류의 상세 원인은 서버 로그에 남기고 응답에는 일반적인 안내를 제공합니다.
HEAD처럼 HTTP 규칙상 본문을 보내지 않는 응답은 JSON 본문을 강제하지 않습니다.
네트워크 단절·CORS 실패·프록시의 HTML 오류는 이 형식으로 보장할 수 없습니다. 응답이 이미 시작된 스트리밍 오류는 별도 계약이 필요합니다.

프론트는 실제 HTTP 상태를 우선하고 `code`로 분기합니다. `detail` 문구를 비교하거나 모든 코드를 알고 있다고 가정하지 않습니다.
알 수 없는 오류 코드나 계약과 다른 응답도 발생할 수 있습니다. 구체적인 구현 책임과 처리 방법은 [백엔드 개발 가이드](../guides/backend.md#오류-처리-구현과-연동)를 참고합니다.

## OpenAPI 연결

`/openapi.json`의 설명에 현재 공통 오류 적용 범위와 422 미적용 상태를 기록합니다. 등록된 API에는 공통 500 응답으로 일반 오류 스키마 `ErrorResponse`를 연결합니다. 이 모델은 네 개의 필수 필드와 현재 구현한 상태·코드, 빈 배열만 허용하는 `errors`를 표현하며 미정인 필드 오류 항목을 정의하지 않습니다.

400·404 등 기능에서 발생하는 오류는 해당 기능의 실제 조건을 정한 뒤 라우트별 응답에 선언합니다. 미등록 경로 404와 잘못된 메서드 405는 등록된 모든 작업의 오류로 나열하지 않고 공통 적용 범위에서 설명합니다. `GET /health`에는 업무 오류를 추가하지 않습니다.

## 구현 완료 기준

- 공통 코드 표의 400·422·404·405·500이 실제 HTTP 상태·발생 조건과 일치하는지 통합 테스트로 확인합니다. 업무별 오류는 기능을 도입할 때 추가합니다.
- 실제 HTTP 상태, 콘텐츠 유형, 고정 필드·타입, 빈 `errors`, 필드 이름·복수 오류·필수 헤더를 확인합니다.
- 내부 오류 내용이나 입력 원문이 응답에 포함되지 않는지 확인합니다.
- 기능별 API 문서·OpenAPI 오류 스키마·실제 응답을 대조합니다. 자동 타입 생성 도입 여부는 별도 결정입니다.

현재 일반 오류 400·404·405·500은 위 기준에 맞춰 구현·검증하며 [health 계약](health.md)의 성공 응답을 유지합니다. 422 공통 형식·필드 오류 항목·복수 오류 변환의 구현과 검증은 남아 있습니다.
