# 프론트·백엔드 계약 검토

> 상태: 검토안. 아래 제안은 아직 전역 API 규칙으로 채택하지 않았습니다.
> 합의한 계약은 [공통 오류](errors.md)·[필드 네이밍](naming.md), 구현한 API는 [API 목차](index.md)에서 확인합니다.

모든 항목을 지금 구현하지 않습니다. 첫 기능을 함께 만들기 전에 필요한 항목을 선택합니다. 확정 본문의 위치와 검토 완료 후 처리는 [API 문서별 책임](index.md#문서별-책임과-기능별-명세-위치)을 따릅니다.

## 첫 기능 연결 전에 맞출 항목

| 항목 | 맞춰야 하는 이유·질문 | 권장 시작안 — 미확정 |
|---|---|---|
| 생략·null·빈 값 | 필드를 안 보낸 것과 null·빈 문자열·빈 배열이 같은 의미인가? | PATCH는 생략 시 유지, null로 지울 수 있는 필드는 명시. 빈 목록은 `[]` |
| 날짜·시간 | 날짜만 있는 값과 시각을 어떻게 구분하고 어느 시간대를 쓰는가? | 날짜는 `YYYY-MM-DD`, 시각은 UTC·시간대가 명시된 RFC 3339 문자열. 화면에서 현지 시간 변환 |
| ID·정밀한 숫자 | 식별자를 숫자로 계산하는가? 큰 정수·금액의 정밀도는 어떻게 유지하는가? | ID는 문자열 우선 검토. DB 키 타입·금액 단위·소수 표현은 별도 명시 |
| 성공 응답 | 객체를 직접 반환할지 `{data: ...}`로 감쌀지? 생성·삭제 응답은 무엇인가? | 기능에 필요한 최소 형태로 통일. 204를 사용하면 JSON 파싱하지 않음. 기존 `/health`는 별도 계약 유지 |
| 필드별 오류 | 중첩 객체·배열 위치, body·query·path, 필드가 없는 오류를 어떻게 표시하는가? | 결정 보류. 첫 입력 폼·기능 API 개발 시 실제 요청을 기준으로 경로·요청 위치를 합의하고 변환 핸들러 구현 |
| 계약과 타입 | 프론트의 TypeScript 타입과 실제 API가 달라지는 것을 어떻게 찾는가? | OpenAPI 타입 생성 검토. 문서·스키마·실제 응답 테스트를 함께 갱신하고 수신 JSON 검증은 별도로 처리 |

날짜·null·성공 응답 규칙은 [오류 계약](errors.md)의 고정 타입과 별개의 결정입니다. 오류 본문의 `status`는 정수, health 성공 본문의 `status`는 문자열 `"ok"`로 서로 다른 스키마입니다.

## 해당 기능을 도입할 때 맞출 항목

| 시점 | 항목 | 결정할 내용 |
|---|---|---|
| 목록 화면 | 페이지·정렬·검색 | page 또는 cursor, 기본·최대 크기, 다음 페이지·총 개수, 허용 필드, 정렬 동률 처리 |
| 로그인·권한 | 인증과 세션 | 쿠키 또는 Bearer, 만료·갱신, 401·403 처리, 로그아웃, 쿠키 사용 시 CSRF 대응 |
| 프론트 실행·배포 | 연결 주소·CORS | 개발 프록시, API 기본 주소, 허용 Origin, credentials, 프론트가 읽을 응답 헤더 |
| 저장·생성 요청 | 시간 제한·재시도·중복 | 클라이언트 타임아웃이 서버 취소를 뜻하는지, 재시도 대상, 중복 제출·멱등성 처리 |
| 파일·이미지 | 업로드·다운로드 | multipart 필드명, 허용 형식·용량, URL 유효기간, 접근 권한 |
| AI 응답 | 스트리밍·긴 작업 | 일반 JSON 또는 SSE 등 전송 방식, 시작·진행·완료·실패 이벤트, 중단·재연결, 생성 비용과 중복 요청 |

API 키와 서버 전용 비밀 값은 프론트 계약의 입력값으로 넘기지 않습니다. 브라우저 요청 취소나 연결 종료만으로 서버의 DB·AI 작업이 취소됐다고 간주하지 않습니다.
실제 사용하는 기능에 맞게 시간 제한과 재시도를 정하고, 저장·유료 생성 요청을 무조건 재시도하는 공통 정책은 두지 않는 안을 권장합니다.

## 결정과 확인 방법

1. 해당 기능의 요청·성공·실패 JSON 예시와 인수 조건을 작성합니다.
2. 미정 항목 중 해당 기능이 사용하는 부분만 합의합니다. 확정된 본문은 공통 계약 또는 기능별 명세로 옮기고 이 목록에는 원본 링크만 남기거나 해당 행을 제거합니다.
3. 백엔드 스키마·OpenAPI·응답 테스트와 프론트 타입·요청 처리의 일치를 확인합니다.
4. mock 화면 검증과 실제 백엔드 연결 검증을 구분해 PR에 기록합니다.

필드 삭제·타입 변경·오류 코드 의미 변경처럼 호출부에 영향을 주는 변경은 관련 프론트 수정과 함께 계획합니다.
오류·네이밍 계약을 문서화한 것만으로 인증·프론트 도구 선택까지 확정된 것은 아닙니다.
