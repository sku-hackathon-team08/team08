# 신고 입력·분석·최종 전송

> 상태: 아래 사용자 흐름 확정. 제한 수치와 실패 대응은 미정 표시를 따릅니다. 관련: [신고 처리](report-lifecycle.md).

## 스태프 음성 신고

1. 홈의 신고 버튼으로 입력 화면을 엽니다. 길게 눌러 즉시 신고하지 않습니다.
2. 터치로 녹음을 시작하고 종료합니다. 화면 전체를 탭하면 취소되던 이전 동작은 적용하지 않습니다.
3. 음성을 텍스트로 변환하고 AI가 내용을 정리합니다. 원문과 요약, 유형·위험도 제안, 위치를 확인합니다. 이번에는 현재 구역을 자동 판정하지 않습니다.
4. 텍스트는 같은 화면에서 수정합니다. 유형·위험도 옆 편집 버튼은 선택 바텀시트를 열고, 적용하면 확인 화면에 반영합니다.
5. ‘전송하기’를 눌러 최종 접수합니다. 분석만 끝난 초안은 관제 신고 목록에 나타나지 않습니다.

## 스태프 텍스트 신고

음성과 같은 확인 단계를 거칩니다. 텍스트 입력 → **내용 확인** → AI 분석 결과 확인·수정 → **전송하기** 순서입니다. 입력 직후 바로 접수하는 이전 흐름은 적용하지 않습니다.

## 분류와 원문

유형은 **긴급·시설·혼잡·미아/분실·기타** 5종입니다. 미아와 분실은 하나의 유형이며 별도 소란 유형은 두지 않습니다. 위험도는 **일반·주의·긴급** 3단계입니다. 유형의 ‘긴급’과 위험도의 ‘긴급’은 별개 선택값입니다.

AI는 위험 신호를 추출하고 규칙이 위험도를 제안합니다. 사용자가 변경한 내용으로 원문이나 최초 AI 제안을 덮어쓰지 않습니다. 최종 전송 전 변경은 확인 화면의 초안이며, 관리자 배정 시 분류 확정은 [신고 처리](report-lifecycle.md)를 따릅니다.

## 위치와 통신 상태

스태프는 아래 고정 위치를 사용하며 이번에는 구역 판정을 하지 않습니다. 현재 구현 범위에서는 GPS를 사용하지 않으며 사전 배정 구역으로 대체하지 않습니다. GPS 미수신 조사 [#46](https://github.com/sku-hackathon-team08/team08/issues/46)은 GPS 미사용 결정으로 범위에서 제외합니다.

통신 단절 시 전송 대기임을 표시하고 재전송할 수 있어야 합니다. 실제 접수 전에는 ‘접수 완료’로 보이지 않아야 합니다. 재전송으로 같은 신고가 중복 접수되지 않는 것을 제품 기대 결과로 두며, 저장·재전송·중복 방지 방법은 API 단계에서 설계합니다.

## 오늘 데모의 고정 위치

> 확정 · 2026-09-11 사용자 지정. 행사 장소와 시연 장소가 달라 오늘 데모는 실제 GPS 대신 아래 좌표를 하드코딩합니다. 현재 구현 범위에서는 GPS를 사용하지 않습니다. 추후 실제 GPS를 도입한다면 별도 요구사항과 검증 작업을 정의합니다.

```json
{
  "lng": 126.8970733,
  "lat": 37.5683536
}
```

- 스태프의 데모 위치·신고 위치는 위 한 지점을 사용합니다. GPS 권한이나 현재 기기 위치를 기다리지 않습니다.
- 3D 지도 마커 높이는 지도 로딩 후 계산한 `modelGroundHeight + 0.44`m입니다. 기준 높이가 준비되기 전에는 마커를 표시하지 않으며, 기준 높이가 갱신되면 마커도 갱신합니다. `0.44`m를 절대 높이로 쓰지 않습니다.
- 화면에는 ‘데모 위치 사용 중’을 표시합니다. 지도 높이는 렌더링 값이며 신고 API의 위도·경도와 분리합니다. 실제 GPS 정확도·수신 시각으로 기록하지 않습니다.
- 구역 판정은 이번 범위에서 제외합니다. 신고의 zone은 null이며 지도 seed의 가상 구역과 분리합니다.
- 관리자 직접 신고는 기존대로 지도에서 선택한 지점을 사용합니다.
- 검증: 데모 위치가 고정 좌표와 일치하고, 마커는 기준 높이 계산 후 0.44m 위에 표시되며, 신고와 관제 지도에 같은 위도·경도가 이어져야 합니다. GPS 실측 검증과 구분합니다.

현재 별도 데모 작업의 지도 코드에는 위 좌표·높이 오프셋이 반영되어 있습니다. 이 브랜치의 스태프 신고·관제 API 연동은 아직 미구현이므로 위 검증을 통과한 것으로 표시하지 않습니다.

## 관리자 직접 신고

지도에서 신고 위치를 선택한 뒤 유형과 텍스트를 입력합니다. 위험도를 직접 고르는 입력 컨트롤은 두지 않고 분석·규칙 제안을 사용합니다. 유형은 공통 5종을 따릅니다. 신고 생성과 담당 배정은 별개 동작이며 담당 배정은 ‘직접 처리하기’에서 이루어집니다.

## 인수 조건

- AC-I01: 음성·텍스트 모두 분석 후 수정할 수 있고 최종 전송 전 관제 목록에 접수되지 않습니다.
- AC-I02: 유형·위험도 바텀시트 적용 결과와 텍스트 수정 내용이 최종 확인 화면에 반영됩니다.
- AC-I03: 수정 후에도 원문과 AI 최초 제안을 구분해 확인할 수 있습니다.
- AC-I04: 홈 롱프레스가 접수를 발생시키지 않습니다.
- AC-I05: 접수되지 않은 대기 신고를 완료로 표시하지 않으며 재전송 결과가 중복 신고로 나타나지 않습니다.
- AC-I06: 관리자 직접 신고 위치는 선택한 지도 위치이며, 생성만으로 담당자가 지정되지 않습니다.

## 해커톤 분석 정책 — 2026-09-11 확정

텍스트는 최대 5,000자, 음성은 10MiB입니다. 분석 결과의 시간 만료는 없고 최종 신고 한 번에만 사용합니다. 실패한 분석으로 신고하지 않으며 사용자가 분석을 재시도합니다. 서버 재시작으로 중단된 분석은 실패로 안내하고 자동 재실행하지 않습니다.

AI가 원문에서 확인한 생명 위협·화재·압사 위험은 긴급, 시설 위험·통행 방해·혼잡은 주의, 나머지는 일반을 제안합니다. 부정되거나 해소된 위험은 신호에서 제외하도록 지시합니다. 스태프는 최종 확인·수정합니다.

## 후속 범위

녹음 중 뒤로가기·취소 UI, 오프라인 대기 보관·앱 종료 복구와 실제 기기 검증은 클라이언트 작업입니다. 장기 운영용 보존·삭제 정책은 별도로 정의합니다.
