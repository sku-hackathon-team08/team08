# Git 협업

> 상태: 검토안. 브랜치·커밋·리뷰·병합 방식은 팀 검토 후 확정합니다.
> 적용 방식: [가이드 목차](index.md#필수-규칙과-권장사항)

## 필수 규칙 제안

- 변경은 작업 브랜치에서 PR로 공유하고 `main`에 병합합니다.
- 공유 브랜치에 강제 push해 다른 사람의 커밋을 덮어쓰지 않습니다.
- PR에는 실제 수행한 검증과 미실행 항목을 구분해 기록합니다.

현재 초기 문서 PR은 비어 있던 `main`의 기준 커밋에서 시작합니다.
아래 방식은 앞으로의 작업을 위한 제안이며 브랜치 보호 설정을 자동으로 적용하지 않습니다.

## 브랜치 권장 형식

`<타입>/<작업명>`처럼 짧은 영문 kebab-case를 권장합니다.
필요하면 작업명에 `fe-`·`be-`를 붙입니다. 사람별 영구 브랜치보다는 작업 단위로 만듭니다.

- `feat/fe-search-page`: 프론트 기능
- `fix/be-input-validation`: 백엔드 수정
- `docs/development-guides`: 공통 문서
- `chore/project-setup`: 초기 설정

에이전트 도구가 `codex/` 같은 브랜치 접두어를 사용하는 경우에도 PR의 범위와 목적이 드러나면 됩니다.

## 커밋 권장 형식

기준은 [Conventional Commits 1.0.0 한국어 명세](https://www.conventionalcommits.org/ko/v1.0.0/)입니다.
아래는 명세의 요약이며, 소문자 타입·한국어 요약·PR 제목 적용은 팀 권장사항입니다.

```text
type(scope)!: 변경 요약

본문

꼬리말
```

- `type`과 요약은 필수이며 콜론 뒤에 공백을 둡니다.
- `(scope)`, `!`, 본문, 꼬리말은 선택입니다. `!`는 호환성을 깨는 변경에만 사용합니다.
- 본문과 꼬리말은 앞부분과 빈 줄로 구분합니다. 본문에는 변경 이유와 영향을 적습니다.
- 명세는 타입의 대소문자를 구분하지 않습니다. 팀에서는 소문자 타입과 간결한 한국어 요약을 권장합니다.
- `feat`는 기능 추가, `fix`는 버그 수정입니다. 나머지 타입은 확장 가능하며 아래 목록은 팀 권장 예시입니다.

한 커밋에는 한 가지 목적을 담습니다.

| 타입 | 변경 목적 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 오류 수정 |
| `docs` | 문서 변경 |
| `refactor` | 동작을 유지하는 코드 구조 변경 |
| `test` | 테스트 추가·수정 |
| `perf` | 성능 개선 |
| `revert` | 기존 커밋 되돌리기 |
| `style` | 공백·포맷 등 동작에 영향 없는 정리 |
| `build` | 빌드 도구·의존성 변경 |
| `ci` | 자동 검사·배포 워크플로우 변경 |
| `chore` | 기타 설정·유지보수 |

```text
feat(frontend): 검색 화면 추가
fix(backend): 입력값 검증 오류 수정
docs: 개발 가이드 추가
test(backend): 경계값 검증 사례 추가
```

### 호환성 변경과 꼬리말

호환성을 깨는 변경은 타입과 관계없이 제목의 `!` 또는 `BREAKING CHANGE:` 꼬리말로 표시합니다.
둘을 함께 사용할 수도 있습니다. `!`만 쓸 때도 요약에서 호환성 변경을 설명합니다.
꼬리말의 `BREAKING CHANGE`는 대문자를 유지하며 `BREAKING-CHANGE`도 허용됩니다.
일반 꼬리말은 `Refs: #123`처럼 토큰과 값을 쓰고, 여러 단어의 토큰은 `Reviewed-by`처럼 하이픈으로 연결합니다.

아래는 형식 설명용 예시이며 현재 프로젝트의 API 계약은 아닙니다.

```text
feat(api)!: 사용자 응답의 name 필드를 displayName으로 변경

화면에서 사용하는 표시 이름과 필드명을 일치시킨다.

BREAKING CHANGE: 기존 name 필드를 읽던 클라이언트는 displayName으로 변경해야 한다.
Refs: #123
```

단순 화면 디자인 작업 전체를 `style`로 분류하지 말고 기능 추가·오류 수정 등 실제 목적에 맞춥니다.

## PR·리뷰·병합 권장사항

- 리뷰 가능한 기능이나 목적 단위로 PR을 나누고, 무관한 포맷 변경을 함께 넣지 않습니다.
- PR 제목도 커밋과 같은 형식을 권장합니다. 이는 커밋 메시지를 대상으로 하는 공식 명세에 팀이 추가한 권장사항입니다. 본문에는 문제·변경 후 동작·관련 명세·검증 결과를 적습니다.
- 화면 변경은 필요한 스크린샷을, 계약 변경은 호출부와 호환성 영향을 함께 적습니다.
- 리뷰에서는 명세 일치·오류와 경계 조건·변경 영향을 우선 확인합니다.
- 병합 전 관련 검증 결과와 리뷰 의견을 확인하고, 충돌 해결로 동작이 바뀌었다면 영향을 받는 검사를 다시 수행합니다.
- 머지 방식과 필수 리뷰 수는 추후 합의합니다. CI가 생기면 문서에서 정한 필수 검사와 실제 설정을 맞춥니다.

검증 범위는 [테스트 가이드](testing.md), 전체 개발 흐름은 [SDD](../sdd.md)에 있습니다.
