# 테스트·TDD

> 상태: 백엔드의 unit·integration 폴더 분리를 채택했습니다. 작성·격리·TDD 방식은 권고사항이며 공통 필수 규칙은 아래 제안 상태를 유지합니다. pytest·AnyIO·HTTPX로 상태 확인 테스트와 CI를 구성했습니다.
> 적용 방식: [가이드 목차](index.md#필수-규칙과-권장사항)

## 필수 규칙 제안

- 테스트의 기대값은 요구사항·계약에서 정합니다. 현재 구현을 그대로 복사해 정답으로 삼지 않습니다.
- 테스트 데이터에는 실제 비밀 값이나 개인정보를 사용하지 않습니다.
- 수행한 검사·결과·미실행 이유·알려진 실패를 PR에 기록합니다. mock 검증을 실제 API 통합 검증으로 표시하지 않습니다.

## 변경별 검증 권장사항

| 변경 | 우선 확인할 내용 |
|---|---|
| 계산·검증·상태 전이 | 정상·경계·실패 사례의 단위 테스트 |
| API·데이터 저장 | 요청·응답·오류 계약, 저장 결과, 필요한 통합 테스트 |
| 기능 오류 수정 | 오류를 재현하는 회귀 테스트와 수정 후 결과 |
| 화면 동작 | 사용자 흐름, 적용되는 로딩·빈 상태·오류, 필요한 컴포넌트 테스트 |
| 핵심 데모 흐름 | 실제 API 연결 상태에서 시작부터 완료까지 통합 또는 E2E 확인 |
| 문서·링크·단순 배치 | 링크·내용 검토 또는 시각 확인. 변경을 그대로 따라 쓰는 테스트는 추가하지 않음 |

모든 변경에 같은 테스트 종류를 요구하지 않습니다. 영향·실패 비용·반복 가능성에 맞게 선택합니다.
탐색용 프로토타입과 화면 배치는 수동 검증으로 시작할 수 있고, 동작이 정해진 핵심 로직은 자동 테스트를 우선합니다.

## TDD 적용 권장사항

TDD(Test-Driven Development)는 구현 단계에서 테스트를 먼저 작성하는 방식입니다.
[SDD](../sdd.md)가 명세에서 개발 전체를 연결한다면, TDD는 그 흐름의 구현·검증 단계에 적용합니다.

핵심 계산·입력 검증·상태 전이·오류 재현처럼 기대 결과가 명확한 부분에 우선 적용합니다.
요구사항이 미정이면 먼저 기대 동작을 구체화하고, 탐색 코드의 현재 동작을 그대로 계약으로 확정하지 않습니다.

1. **실패하는 테스트:** 명세의 한 가지 기대 동작을 테스트로 작성하고 예상한 이유로 실패하는지 확인합니다.
   실행 환경이나 import 오류로 실패한 것은 기대 동작을 검증한 결과가 아닙니다.
2. **최소 구현:** 해당 기대 동작을 만족하는 코드를 작성해 테스트를 통과시킵니다.
3. **리팩터링:** 동작을 유지하면서 구조를 정리하고 관련 테스트가 계속 통과하는지 확인합니다.

예를 들어 명세에서 수량을 1 이상으로 정했다면 정상 수량·경계값·범위를 벗어난 입력의 기대 결과부터 작성할 수 있습니다.
이는 방식 설명용 예시이며 현재 프로젝트의 요구사항이 아닙니다.

TDD의 중간 작업 커밋과 병합 단위는 [원자적 커밋 가이드](git-workflow.md#원자적-커밋-권장사항)를 참고합니다.

## 테스트 작성과 실행

- 테스트 이름에는 조건과 기대 동작이 드러나게 적고, 서로 실행 순서에 의존하지 않게 만듭니다.
- 시간·난수·외부 API처럼 변동하는 요소는 필요한 경계에서 제어합니다.
- mock은 외부 의존성을 분리할 때 사용하되, 중요한 연동은 별도의 통합 검증으로 확인합니다.
- 구현 중에는 관련 검사를 빠르게 실행하고, PR 전에는 변경 범위에 맞는 검사를 수행합니다.
- 통과 후에는 새 변경·실패·미해결 우려가 있을 때 필요한 검사를 추가하거나 반복합니다.
- 설치·실행·검증 명령은 [프론트 README](../../frontend/README.md)와 [백엔드 README](../../backend/README.md)에 기록합니다.

## 백엔드 테스트

### 분류와 폴더 구조

테스트가 **실제로 연결하는 범위**를 기준으로 나눕니다. 함수가 위치한 레이어나 동기·비동기 여부로 분류하지 않습니다.

| 위치 | 검증 범위 | 예시 |
|---|---|---|
| `tests/unit/` | DB·네트워크 없이 독립된 로직. 필요한 외부 의존성만 fake·mock으로 대체 | 계산·값 변환·서비스의 정상·오류 분기 |
| `tests/integration/` | 앱·라우터·스키마 또는 저장소·DB처럼 여러 구성요소를 실제로 연결 | HTTP 요청·응답 계약, 향후 테스트 DB 저장·조회 |

```text
backend/tests/
├── conftest.py               # 두 종류에 공통인 fixture
├── unit/                    # 독립 로직 테스트, 현재 비어 있음
└── integration/
    └── test_health.py        # ASGI 앱의 요청·응답 검증
```

`unit/`은 `.gitkeep`으로 경로만 유지합니다. 폴더를 채우기 위한 더미 테스트는 추가하지 않습니다.
파일은 `test_<기능>.py`, 함수는 `test_<조건>_<기대결과>` 형태를 권장합니다.
테스트가 늘면 각 폴더 안을 기능별로 나누고, 비어 있는 레이어 폴더를 미리 복제하지 않습니다.
pytest의 `importlib` 모드를 설정해 두 폴더에 같은 파일명이 있어도 수집할 수 있게 합니다.
테스트 파일끼리 import하지 않고, 재사용 준비 코드는 fixture로 제공합니다.

현재 `/health` 테스트는 라우팅·응답 스키마·JSON 변환을 함께 확인하는 통합 테스트입니다.
실제 ASGI 앱을 프로세스 안에서 호출하며 별도 서버·네트워크·DB를 사용하지 않습니다. 브라우저부터 배포 서버까지 확인하는 E2E 테스트는 아닙니다.
외부 API만 mock으로 대체한 앱 테스트도 통합 폴더에 둘 수 있지만, 실제로 확인한 연결과 대체한 경계를 PR에 구분해 적습니다.

### 작성 권고

- **준비 → 실행 → 확인:** 입력·의존성을 준비하고 대상 동작을 실행한 뒤 계약의 기대 결과를 확인합니다. 각 단계에 주석을 의무적으로 붙이지는 않습니다.
- **하나의 동작에 집중:** 정상·경계·실패 사례를 필요한 만큼 나눕니다. 하나의 응답에 대한 상태 코드·본문처럼 관련된 assertion은 함께 둘 수 있습니다.
- **관찰 가능한 결과 확인:** 반환값·오류·저장 결과를 우선 확인합니다. 내부 함수 호출 순서를 그대로 따라 쓰지 않고, 호출 횟수 자체가 요구사항일 때만 검증합니다.
- **필요한 경계만 대체:** 유닛 테스트에서는 DB·외부 API 등을 분리합니다. 통합 테스트에서는 확인하려는 연결을 mock으로 끊지 않습니다.
- **결정적인 실행:** 현재 시간·난수·환경변수는 필요할 때 고정하거나 주입합니다. 성공할 때까지 반복하거나 임의의 sleep을 늘려 실패를 숨기지 않습니다.
- **오류 수정과 TDD:** 재현 가능한 버그는 실패 사례를 먼저 확인합니다. 핵심 로직은 위 TDD 흐름을 우선 고려하고, 모든 변경에 TDD·동일한 테스트 개수를 강제하지 않습니다.

### Fixture와 상태 격리 권고

Fixture는 테스트의 데이터·자원을 준비하고 정리하는 pytest 함수입니다.

- 특정 파일에서만 쓰는 fixture는 그 파일에 둡니다. 여러 파일이 공유하면 가장 가까운 `conftest.py`에 두며, 루트에는 두 종류가 함께 쓰는 것만 둡니다.
- 현재 루트의 `anyio_backend`는 `asyncio`를 선택합니다. 비동기 테스트에는 `@pytest.mark.anyio`를 사용하고, 순수 동기 로직은 일반 `def`로 테스트합니다.
- 변경 가능한 상태는 테스트마다 새로 준비하는 기본 `function` 범위를 우선합니다. 넓은 범위의 fixture는 상태가 섞이지 않는 경우에만 사용합니다.
- 클라이언트·파일·향후 DB 세션은 context manager나 `yield` fixture로 정리합니다. 환경변수는 `monkeypatch`, 임시 파일은 `tmp_path`를 활용합니다.
- FastAPI `dependency_overrides`를 사용하면 실패한 테스트 뒤에도 원래 상태로 복원합니다. 전역 앱 상태를 다음 테스트에 남기지 않습니다.
- DB 도입 시 별도 테스트 DB를 준비하고 테스트별 데이터 격리·정리 방식을 함께 구현합니다. 개발용 SQLite 파일이나 운영 DB를 재사용하지 않습니다.
- 외부 서비스의 실제 호출은 기본 테스트에 넣지 않습니다. 필요해지면 별도 실행 조건·자격 증명·비용과 검증 범위를 정합니다.

DB 도구·fixture는 아직 구현하지 않았습니다. PostgreSQL을 채택하면 그 환경에서 필요한 통합 검증을 추가하며 SQLite 테스트 결과만으로 PostgreSQL 호환성을 보장하지 않습니다.
현재 비동기 앱 호출과 향후 lifespan 처리는 [백엔드 개발 가이드](backend.md#동기비동기-사용-기준), 전체·종류별 실행 명령은 [백엔드 README](../../backend/README.md#코드-검사와-테스트)를 참고합니다.
위 작성 권고를 검사하는 별도 린터·커버리지 하한·테스트 종류별 CI job은 추가하지 않습니다.

## 추후 결정

- 프론트 테스트 프레임워크와 테스트 파일 위치
- 프론트 CI와 그 필수 검사 여부. 백엔드는 모든 PR에서 실행하며 `Backend checks` 통과를 병합 조건으로 적용. 자세한 조건은 [백엔드 CI](backend.md#ci) 참고
- E2E 대상과 통합 테스트 환경
- 커버리지 기준의 필요 여부. 숫자를 정하기 전에 핵심 동작의 검증 범위를 정합니다.
