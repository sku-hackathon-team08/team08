# 테스트·TDD

> 상태: 검토안. 테스트 도구·명령·CI는 기술 스택 확정 후 정합니다.
> 적용 방식: [가이드 목차](index.md#필수-규칙과-권장사항)

## 필수 규칙 제안

- 테스트의 기대값은 요구사항·계약에서 정합니다. 현재 구현을 그대로 복사해 정답으로 삼지 않습니다.
- 테스트 데이터에는 실제 비밀 값이나 개인정보를 사용하지 않습니다.
- 수행한 검사·결과·미실행 이유·알려진 실패를 PR에 기록합니다. mock 검증을 실제 API 통합 검증으로 표시하지 않습니다.

## 변경별 검증 권장사항

| 변경 | 우선 확인할 내용 |
|---|---|
| 계산·검증·상태 전이 | 정상·경계·실패 사례의 단위 테스트 |
| API·데이터 저장 | 요청·응답·오류 계약, 저장 결과, 필요한 통합 테스트 |
| 기능 오류 수정 | 오류를 재현하는 회귀 테스트와 수정 후 결과 |
| 화면 동작 | 사용자 흐름, 적용되는 로딩·빈 상태·오류, 필요한 컴포넌트 테스트 |
| 핵심 데모 흐름 | 실제 API 연결 상태에서 시작부터 완료까지 통합 또는 E2E 확인 |
| 문서·링크·단순 배치 | 링크·내용 검토 또는 시각 확인. 변경을 그대로 따라 쓰는 테스트는 추가하지 않음 |

모든 변경에 같은 테스트 종류를 요구하지 않습니다. 영향·실패 비용·반복 가능성에 맞게 선택합니다.
탐색용 프로토타입과 화면 배치는 수동 검증으로 시작할 수 있고, 동작이 정해진 핵심 로직은 자동 테스트를 우선합니다.

## TDD 적용 권장사항

TDD(Test-Driven Development)는 구현 단계에서 테스트를 먼저 작성하는 방식입니다.
[SDD](../sdd.md)가 명세에서 개발 전체를 연결한다면, TDD는 그 흐름의 구현·검증 단계에 적용합니다.

핵심 계산·입력 검증·상태 전이·오류 재현처럼 기대 결과가 명확한 부분에 우선 적용합니다.
요구사항이 미정이면 먼저 기대 동작을 구체화하고, 탐색 코드의 현재 동작을 그대로 계약으로 확정하지 않습니다.

1. **실패하는 테스트:** 명세의 한 가지 기대 동작을 테스트로 작성하고 예상한 이유로 실패하는지 확인합니다.
   실행 환경이나 import 오류로 실패한 것은 기대 동작을 검증한 결과가 아닙니다.
2. **최소 구현:** 해당 기대 동작을 만족하는 코드를 작성해 테스트를 통과시킵니다.
3. **리팩터링:** 동작을 유지하면서 구조를 정리하고 관련 테스트가 계속 통과하는지 확인합니다.

예를 들어 명세에서 수량을 1 이상으로 정했다면 정상 수량·경계값·범위를 벗어난 입력의 기대 결과부터 작성할 수 있습니다.
이는 방식 설명용 예시이며 현재 프로젝트의 요구사항이 아닙니다.

## 테스트 작성과 실행

- 테스트 이름에는 조건과 기대 동작이 드러나게 적고, 서로 실행 순서에 의존하지 않게 만듭니다.
- 시간·난수·외부 API처럼 변동하는 요소는 필요한 경계에서 제어합니다.
- mock은 외부 의존성을 분리할 때 사용하되, 중요한 연동은 별도의 통합 검증으로 확인합니다.
- 구현 중에는 관련 검사를 빠르게 실행하고, PR 전에는 변경 범위에 맞는 검사를 수행합니다.
- 통과 후에는 새 변경·실패·미해결 우려가 있을 때 필요한 검사를 추가하거나 반복합니다.
- 설치·실행·검증 명령은 [프론트 README](../../frontend/README.md)와 [백엔드 README](../../backend/README.md)에 기록합니다.

## 추후 결정

- 파트별 테스트 프레임워크와 테스트 파일 위치
- CI 필수 검사와 실행 조건
- E2E 대상과 통합 테스트 환경
- 커버리지 기준의 필요 여부. 숫자를 정하기 전에 핵심 동작의 검증 범위를 정합니다.
