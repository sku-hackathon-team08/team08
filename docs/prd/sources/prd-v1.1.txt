브이월드 3D 공간정보 기반 축제 현장 음성 신고·안전 대응 지휘 서비스

버전 1.1 · SKTHON 2026 대응 · v1.0 대비 전면 개정

## 0. 개요

### 0.1 한 줄 정의

무전기가 없는 현장 인력이 말 한 번으로 신고하고, 그 신고가 3D 지도 위에서 관리자에게 닿고, 전 과정이 자동으로 기록되는 축제 현장 지휘 서비스.

### 0.2 v1.0 → v1.1 변경 요약 (팀 전원 확인)

| # | 항목 | v1.0 | v1.1 |
| --- | --- | --- | --- |

| 15 | 취소 | 상태 전이 | 유지 + **"삭제" 표현 금지, 사유와 함께 기록 존치** |

### 0.3 사용자 유형 (2단계)

| 유형 | 인증 | 기기 | 핵심 동작 |
| --- | --- | --- | --- |
| **스태프** | 행사 코드 + 이름 + 소속팀 (세션 기반, 로그인 아님) | 모바일 앱 | 음성/텍스트 신고, 내 신고 내역 확인 |
| **관리자** | 행사 코드 + 이름 (간편 로그인) | **태블릿 전용** | 신고 확인·처리·지원요청, 3D 지도 조회, 리포트 내보내기 |

역할 구분(조장/대리/감독) 없이 로그인한 관리자는 전원 동일 권한. 행사 개설(신청)도 관리자 역할 안에 포함하며 별도 계층을 만들지 않는다. 구역별 라우팅·권한 분화는 MVP 범위 밖.

### 0.4 MVP 범위 확정

| 구분 | 항목 |
| --- | --- |
| **반드시 구현** | 음성 신고 파이프라인, 행사 코드 등록, 3D 지도+핀, 접근 경로 1개, 선점(claim) 잠금, 관리자 처리 액션, 스태프 상태 회신(조용한 갱신), 스태프 신고 내역, 행사 신청 + 구역·게이트 배치, 목록 정렬·필터, 나의 리포트 PDF 내보내기 |
| **목업만** | 가시권 분석, 신고 히트맵, 지자체 에스컬레이션 |
| **미구현** | 결제, 다국어, 관리자 권한 분화, 구역별 자동 라우팅, 행사 신청 승인 절차(신청 즉시 자동 승인), 다크모드, 2D 폴백 |
| **사전 검증 필요** | 브이월드 API의 보행/차량 경로 탐색 제공 여부 — **폴백을 삭제했으므로 미지원 시 대체안을 새로 결정해야 함(1일차 오전 마감)** |

## 1. 핵심 원칙 (프론트·백엔드·디자인 공통 준수)

1. **AI는 판단하지 않고 정리한다.** 유형·긴급도 모두 `AI 추정` 라벨을 달고 노출된다. 긴급도는 AI가 신호만 추출하고 규칙 테이블이 등급을 산정하며, 최종 확정은 사람이 한다. 관리자는 언제든 수동으로 값을 바꿀 수 있고, 확정 주체가 기록된다.
2. **신고는 사라지지 않는다.** 자동 병합하지 않으며(연관 신고 UI 자체를 두지 않는다), 취소도 삭제가 아니라 사유와 함께 남는 상태 전이다. 화면 문구에 "삭제"라는 단어를 쓰지 않는다.
3. **선점(claim) 단일 소유.** 신고는 전원에게 노출되지만 처리 권한은 최초 확인자 1인에게만 있다. 동시 확인 시 서버 선착 1건만 성공한다.
4. **알림은 조용히.** 관리자 처리 상태 변경은 스태프 화면에 새 푸시를 띄우지 않고 상태 줄만 갱신한다.
5. **음성이 1순위, 직접 입력이 2순위.** 두 경로를 같은 화면에 함께 노출하되, 시각적 위계는 음성 > 텍스트로 명확히 둔다.
6. **기기는 각 1종.** 스태프 = 모바일 앱, 관리자 = 태블릿. 브레이크포인트 다중 대응을 하지 않는다.

## 2. 화면 ID 체계

| ID | 화면 | 대상 |
| --- | --- | --- |
| **L1** | 랜딩 (로그인 / 행사신청 2분기) | 공통 |
| **E1** | 행사 신청 → 구역·게이트 배치 → 코드 발급 결과 | 관리자 |
| ~~E2~~ | **삭제** | — |
| **A1** | 관리자 로그인 (행사 코드 + 이름) | 관리자 |
| **A2** | 지도 대시보드 (기본 탭) | 관리자 |
| **A3** | 나의 리포트 (PDF 내보내기) | 관리자 |
| **A4** | 신고 상세 (구 "04 신고상세") | 관리자 |
| **S1** | 참가자 등록 (코드 + 이름 + 소속팀) | 스태프 |
| **S2** | 신고 홈 (메인 버튼 + 신고 내역 버튼 + 내 위치) | 스태프 |
| **S3** | 신고 입력 (음성 / 직접 입력하기) | 스태프 |
| **S4** | AI 분석 결과 확인·수정 → 전송 | 스태프 |
| **S5** | 내 신고 내역 | 스태프 |

> 기존 와이어프레임의 숫자 번호(04, 10번, 2번 등)는 위 ID로 통합한다. 디자인 파일 페이지명도 동일 ID로 맞춘다.
> 

### 2.1 핵심 플로우

```
[진입] L1 랜딩
  ├─ [로그인] → A1
  └─ [행사신청] → E1

[E1 행사 신청]
행사명·일정·장소 입력 → 3D 지도에서 구역 폴리곤 그리기 → 게이트 핀 배치
  → 신청 완료(자동 승인) → 행사 코드 + 구역이 표시된 3D 렌더링 결과 화면

[스태프]
S1 코드+이름+소속팀 입력(세션 생성) → S2 홈(내 위치·내 구역 표시, 신고 내역 버튼)
  → (탭) S3 녹음 → STT/LLM 구조화 → S4 확인·수정 → 전송 → S2 복귀
  → (S3에서 '직접 입력하기') → 텍스트 입력 → S4 동일 경로
  → (S2에서 롱프레스 1.2s) 확인 없이 즉시 응급 전송 (전송 중 오버레이 없음, 결과만 표시)
  → S2/S5 상태 줄 수신: 접수 → 처리중(담당자명) → 완료/취소

[관리자]
A1 로그인 → A2 지도 대시보드(기본)
  A2: 상단 통계 칩(총/미확인/처리중/완료)
      좌: 3D 지도 + 핀 + 접근경로 / 우하단 직접 신고 플로팅 버튼
      우: 신고 목록 (정렬: 긴급순·최신순 / 필터: 유형·상태)
      카드 탭 → A4 신고 상세
  A4: [뒤로가기] 상단 고정
      원문 블록(스태프가 말하거나 입력한 내용) + AI 추정 필드(유형·긴급도·위치)
      [내가 처리] 탭 → 확인 프롬프트(추정값 확정 또는 수정) → 선점 시도
        성공 → IN_PROGRESS, [완료]/[취소(사유 필수)]/[지원요청]
        실패 → "이미 OOO님이 확인했습니다" 토스트 후 잠금 뷰
  A3: 내가 처리한 신고 목록 + [PDF 내보내기]
```

## 3. 상태 모델 (백엔드·프론트 공통 스펙)

### 3.1 상태 값 (5종, v1.0과 동일)

| status | 진입 조건 | 소유자 필요 |
| --- | --- | --- |
| `RECEIVED` (접수) | 스태프/관리자 전송 | 없음 |
| `IN_PROGRESS` (처리중) | `PATCH /reports/{id}/claim` 성공 | 있음(claimed_by) |
| `RESOLVED` (완료) | 소유자가 결과 메모와 함께 종결 | 소유자만 |
| `CANCELLED` (취소) | 소유자가 사유와 함께 종결, `cancel_reason` 필수 | 소유자만 |
| — `support_requested` (bool) | 소유자가 지원요청 토글 | 상태값 아닌 플래그, 소유권 유지 |

전이는 `RECEIVED → IN_PROGRESS → (RESOLVED | CANCELLED)` 단방향. 되돌리기·넘기기는 MVP 밖.

### 3.2 선점(claim) 동시성 처리

- 조건부 원자적 업데이트: `UPDATE reports SET status='IN_PROGRESS', claimed_by=:uid, claimed_at=now(), urgency=:confirmed, urgency_source='ADMIN_CONFIRMED' WHERE id=:id AND status='RECEIVED'`
- 영향 행 0건이면 이미 선점됨 → **409** 반환
- 클라이언트는 409 수신 시 최신 상태 재조회 → 토스트 후 잠금 뷰 전환
- `version` 정수 컬럼 병행(매 업데이트 +1)

### 3.3 유형(type) 6종

`EMERGENCY(응급)` `LOST(미아/분실)` `FACILITY(시설)` `CROWD(혼잡)` `DISORDER(질서)` `ETC(기타)`

### 3.4 긴급도(urgency) 산정 — AI는 신호만, 등급은 규칙, 확정은 사람

```
1) STT → 원문 텍스트 (transcript_raw)
2) LLM에 고정 스키마로 신호 추출 요청 (등급을 묻지 않음)
   {
     "consciousness_mentioned": bool,   // 의식/호흡/출혈 언급
     "child_lost": bool,                // 아동 미아
     "multiple_people": bool,           // 다수 인원
     "hazard_proximity": bool,          // 트러스 등 등록 시설물 인접
     "crowd_pressure": bool             // 혼잡·압박 표현
   }
3) 규칙 테이블 매핑 (코드에 고정, 문서화):
   긴급 = consciousness_mentioned OR child_lost OR multiple_people
   주의 = hazard_proximity OR crowd_pressure
   일반 = 그 외
4) urgency_source = AI_SUGGESTED 로 저장, 화면에 [AI 추정] 배지 상시 노출
5) 관리자가 A4에서 [내가 처리] 시 확인 프롬프트로 확정 또는 변경
   → urgency_source = ADMIN_CONFIRMED, status_logs에 변경 전/후 기록
6) 파싱 실패 시 전량 "주의"로 낙하 (안전 쪽으로 실패)
```

유형(type)도 동일하게 `type_source` 를 두고 [AI 추정] 배지를 붙이며, 확인 프롬프트에서 수정 가능하다. **스태프 화면(S4)에서도 AI가 잡은 초안을 수동으로 바꿀 수 있다.**

### 3.5 "미확인" 정의 (변경)

- **접수**: `status = RECEIVED` 전체
- **미확인**: `status = RECEIVED` 이면서 `now() - created_at > 임계`
- 임계: 긴급 3분 / 주의 10분 / 일반 30분
- 미확인 진입 시 → 긴급도 한 단계 자동 승격 + 관리자 전원 화면에 강조(테두리 강조 + 목록 최상단 고정). cron 또는 지연 큐로 구현
- A2 상단 통계 칩은 `총 / 미확인 / 처리중 / 완료` 4종 유지하되, 미확인 칩은 위 정의를 따른다

### 3.6 취소·삭제 정책 (신규)

- 관리자의 취소는 **상태 전이**이며 데이터는 삭제되지 않는다. `cancel_reason` 필수, `status_logs`에 사유·시각·행위자 기록
- 취소된 신고는 목록에서 사라지지 않고 `취소` 배지 + 사유 요약과 함께 표시된다(기본 필터에서는 접힘 상태, 필터로 노출 가능)
- 확인 프롬프트 문구는 전 화면 **"접수를 취소하시겠습니까?"** 로 통일한다. 기존 와이어프레임의 "신고 내역을 삭제" 문구는 실제 동작(삭제 아님)과 어긋나므로 사용하지 않는다
- 스태프에게는 자기 신고를 삭제하는 기능을 제공하지 않는다

## 6. AI 파이프라인

```
[음성 파일] → STT(Whisper 등) → 원문 텍스트
             ↓
[원문 텍스트] → LLM 호출 (Claude API 등)
   - 시스템 프롬프트: "다음 항목을 텍스트에서 찾아 true/false와 위치·유형만 JSON으로 반환하라.
     등급이나 우선순위는 판단하지 말 것."
   - 출력 스키마 고정 (3.4 참조)
             ↓
[신호 JSON] → 규칙 함수(코드, LLM 아님) → urgency 산정
             ↓
[구조화 결과] → reports 저장, urgency_source/type_source = AI_SUGGESTED
             ↓
[S4] 스태프 수동 수정 가능 → STAFF_EDITED
[A4] 관리자 확정/수정 → ADMIN_CONFIRMED (status_logs 기록)
```

프롬프트에 등급을 직접 묻지 않는 것이 원칙 위반 방지의 핵심 — 코드 리뷰 시 반드시 확인. 파싱 실패 시 주의 등급 폴백 + 로그.

## 7. 프론트엔드 요구사항

### 7.1 L1 · 랜딩

- 버튼 2개만: `[로그인]` `[행사 신청]`. 그 외 요소 최소화
- 서비스 한 줄 정의 + 3D 지도 스틸 이미지 배경(로딩 비용 없는 정적 이미지)

### 7.2 E1 · 행사 신청

- 3단계 스텝퍼: ① 행사 정보 입력 → ② 3D 지도에서 구역 폴리곤 그리기 + 게이트 핀 배치 → ③ 완료
- ③ 결과 화면에 **행사 코드(대문자, 복사 버튼)** 와 **구역·게이트가 표시된 3D 렌더링** 을 함께 노출
- 구역은 최소 1개, 게이트는 최소 1개 등록해야 완료 가능
- 승인 절차 없음(신청 = 개설). "신청"이라는 표현은 유지하되 대기 상태 UI는 만들지 않는다

### 7.3 S1 · 참가자 등록

- 입력 3개: **참가자(행사) 코드 / 이름 / 소속팀**. QR 스캔 없음
- 코드는 대문자 자동 변환, 오류 시 필드 하단 인라인 메시지
- 성공 시 `session.staff` 로컬 저장, 재실행 시 S2로 바로 진입

### 7.4 S2 · 신고 홈

- 메인 신고 버튼: 지름 150px, 탭 = S3 진입, 롱프레스 1.2초 = 즉시 응급 전송
- 롱프레스 진행 표시: 원형 진행률 링(`stroke-dashoffset`), 0.1초 단위, 1.2초 미만에 떼면 즉시 취소. 진동 API 가능 시 완료 시점 피드백
- **응급 전송 시 "전송 중" 오버레이를 띄우지 않는다.** 버튼 상태 변화 + 완료 후 "전송됨" 결과 표시로 끝낸다
- 상단: **내 위치와 배정 구역 표시.** 지도에는 자기 위치만 나타나며, 다른 스태프나 다른 신고는 표시하지 않는다
- 하단: `[신고 내역]` 버튼 → S5
- 진행 중인 내 신고가 있으면 상태 줄(접수 / 처리중 · 담당자명 / 완료)을 조용히 갱신

### 7.5 S3 · 신고 입력

- 화면 위계: **음성 녹음이 1순위(대형 버튼), '직접 입력하기'가 2순위(항상 노출, 숨기지 않음)**
- 녹음 중 취소: 별도 X 버튼 없이 화면 전체가 취소 히트 영역, 확인 팝업 없이 즉시 취소
- placeholder·안내 문구는 실제 발화 수준의 짧은 예시 사용: "이 구역에 사람 다쳤어요" 형태. "내용을 입력하세요" 같은 일반론 금지
- 전문용어 노출 금지(긴급도·선점·구조화 등)

### 7.6 S4 · AI 분석 결과 확인·수정

- AI가 잡은 초안을 표시: 내용 텍스트 / 유형 / 긴급도 — 각각 `[AI 추정]` 배지
- **모든 추정 값은 수동 변경 가능.** 내용은 `<textarea>` 탭 즉시 편집(별도 수정 화면 이동 금지), 유형·긴급도는 칩 선택으로 변경
- 변경 시 `*_source = STAFF_EDITED`
- 전송 버튼 높이 56px 이상, "다시 말하기"와 명확히 분리 배치

### 7.7 S5 · 내 신고 내역

- 내가 보낸 신고만 최신순 표시. 각 항목: 시각 · 요약 · 상태 배지(담당자명 포함)
- 삭제 기능 없음

### 7.8 A2 · 지도 대시보드 (태블릿)

- 상단 통계 칩: 총 / 미확인(3.5 정의) / 처리중 / 완료
- 좌: 브이월드 3D 지도 + 신고 핀 + 접근 경로 오버레이. **2D 전환 토글 없음**
- 우: 신고 목록
    - 정렬: `긴급순` `최신순`
    - 필터: 유형 6종, 상태(접수·처리중·완료·취소)
    - 미확인 건은 정렬과 무관하게 상단 고정 + 강조
- 우하단 플로팅 `[직접 신고]` 버튼 → 관리자용 신고 입력(스태프와 동일 형태 언어, 위험도 직접 선택 불가)
- 카드 탭 → 핀 포커스 + 경로 오버레이, 카드 상세 탭 → A4

### 7.9 A4 · 신고 상세

- **상단 좌측에 뒤로가기 버튼 고정** (A2 목록 위치·스크롤 유지한 채 복귀)
- 화면을 두 블록으로 분리:
    1. **원문 블록** — 스태프가 실제로 말하거나 입력한 내용만. 배경색으로 구분하고 "스태프 입력" 라벨. AI가 덧붙인 문장을 여기에 섞지 않는다
    2. **추정 블록** — 유형 · 긴급도 · 구역 · 좌표. 각 항목에 `[AI 추정]` 배지, 확정 전까지 추정 상태 유지
- 액션: `[내가 처리]` 탭 → **확인 프롬프트**에서 유형·긴급도를 확정하거나 수정 → 확인 시 claim 요청
    - 성공 → IN_PROGRESS, `[완료]` `[취소]` `[지원요청]`
    - 실패(409) → "이미 OOO님이 확인했습니다" 토스트 + 잠금 뷰
- 취소 선택 시: "접수를 취소하시겠습니까?" + 사유 입력(필수). 사유 없이 확인 불가
- 하단에 상태 이력(누가 언제 무엇을 바꿨는지) 타임라인 표시
- **연관 신고 영역 없음**

```
if report.status == RECEIVED:
    render(["내가 처리"])
elif report.status == IN_PROGRESS and report.claimed_by == currentAdmin:
    render(["완료", "취소", "지원요청"])
elif report.status == IN_PROGRESS and report.claimed_by != currentAdmin:
    if report.support_requested:
        render(["지원하기"])
    else:
        render_locked_label(f"{claimer_name} 처리 중")
else:
    render_readonly()   # RESOLVED / CANCELLED
```

### 7.10 A3 · 나의 리포트

- 내가 처리한 신고 목록 + 요약 지표(건수, 평균 소요 시간, 유형 분포)
- **`[PDF 내보내기]` 버튼** — 행사명·기간·담당자명·신고별 시각/구역/유형/긴급도/소요시간/처리결과 표를 포함한 A4 문서 생성
- 구현: 전용 인쇄 레이아웃(print CSS) + 브라우저 PDF 저장. 서버 렌더링은 시간 남을 때 승격

### 7.11 상태 관리 키 값

- `session.staff`: `{staff_session_id, name, team, zone_name}` — 로컬 저장, 만료 시 S1 유도
- `session.admin`: `{admin_id, event_id, token}`
- `report.draft`: S3~S4 임시 편집 상태(전송 전까지 서버 미반영)
- `offlineQueue`: 전송 실패 신고 로컬 큐(IndexedDB), 네트워크 복구 시 지수 백오프 순차 재전송, "전송 대기 중 N건" 표시. 실패를 경고성으로 알리지 않는다

### 7.12 3D 지도

- 행사 전 반경 500m 브이월드 타일 사전 캐싱(발표 중 실시간 타일 로딩 금지)
- 핀 색상: 긴급=danger, 주의=warning, 일반=gray, 완료=success(옅게), 취소=muted
- **2D 폴백 경로 없음** — 3D 렌더링 안정화에 개발 리소스를 집중한다(11번 리스크 참조)

### 7.13 발표/데모 안정성

- GPS 미작동(실내 발표장) 대비 시뮬레이션 모드: 사전 등록 좌표로 대체하는 플래그
- 실사용에서는 주최사가 제공하는 구역·시설 좌표를 사용하지만, MVP는 E1에서 직접 배치한 좌표를 기준으로 동작

## 8. 디자인 요구사항

### 8.1 설계 전제

야외 직사광선, 젖은 손·장갑, 이동 중 한 손 조작, 응급 시 손 떨림. "예쁨"보다 "실패 표면적 최소화"가 우선.

### 8.2 터치 타깃 규격

| 요소 | 기기 | 크기 |
| --- | --- | --- |
| S2 메인 신고 버튼 | 모바일 | 150px 지름 |
| S3 직접 입력하기 버튼 | 모바일 | 높이 52~56px, 상시 노출 |
| S4 전송 버튼 | 모바일 | 높이 56px 이상 |
| A2 카드 액션 버튼 | 태블릿 | 높이 44~52px (3버튼 병렬 시에도 44px 유지) |
| A2 플로팅 직접 신고 | 태블릿 | 56px |
| A4 확인 프롬프트 버튼 | 태블릿 | 높이 52px 이상 |

정밀 드래그·스와이프는 주요 동작 경로에 쓰지 않는다(녹음 취소만 "화면 전체 탭"으로 예외 — 정밀도 요구를 낮추는 방향).

### 8.3 색상 규칙 (상태 의미 고정, 전 화면 동일)

| 상태/의미 | 색상 |
| --- | --- |
| 긴급 | danger(적) |
| 주의 | warning(황/주황) |
| 일반 | gray |
| 처리중(소유) | accent(청) |
| 완료 | success(녹) |
| 취소 | muted gray |
| 지원요청 | warning 강조 배지 |
| AI 추정 배지 | outline + 보조 텍스트 색 (상태색과 절대 겹치지 않게) |

### 8.4 타이포·대비

- 직사광선 대응: hairline(0.5px) 금지, 최소 1.5px 테두리. 정보성 텍스트도 명도 대비 4.5:1 이상
- 라벨 텍스트 11px 미만 금지

### 8.5 마이크로카피 원칙

- 결과 중심 서술: "전송 중"(X) → "전송됨"(O)
- 스태프 화면에 내부 용어 금지(긴급도·선점 → 관리자 화면 전용, 스태프에게는 "응급" 등 일상어)
- **"삭제" 표현 금지** — 취소는 기록에 남으므로 "접수 취소"로 통일
- placeholder는 실제 예시 문장 사용

### 8.6 테마

**다크모드 대응 삭제.** 단일 라이트 테마로 개발하되, 야간 사용을 고려해 대비를 8.4 기준으로 높인다. 색상은 디자인 토큰으로 관리하고 하드코딩하지 않는다(추후 다크모드 재도입 여지만 남김).

## 12. 확인 필요 항목 (팀 결정 대기)

1. **"10번 / 2번 화면"의 취소 문구** — 3.6에서 "접수를 취소하시겠습니까?"로 통일하고 "삭제" 표현을 제거했습니다. 두 화면이 각각 다른 동작(관리자 처리 취소 vs 스태프 신고 회수)을 의도한 것이라면 다시 정해야 합니다
2. **응급 롱프레스 유지 여부** — "응급신고 전송 중 빼기"를 '전송 중 오버레이 제거'로 해석했습니다. 응급 롱프레스 기능 자체를 빼는 것이라면 S2 인터랙션을 단순화해야 합니다
3. **소속팀과 구역의 관계** — 소속팀을 자유 입력 텍스트로 두고, 구역은 신고 좌표로 판정하게 했습니다. 소속팀이 곧 구역 배정을 뜻한다면 팀→구역 매핑을 E1에서 등록해야 합니다
4. **A4 확인 프롬프트 삽입 위치** — [내가 처리] 앞에 프롬프트를 두면 선점 속도가 한 템포 느려집니다. 선점을 먼저 하고 프롬프트를 띄우는 순서로 바꿀지 결정 필요
5. **행사 "신청"의 승인 주체** — MVP는 자동 승인입니다. 심사에서 "누가 승인하나" 질문이 나올 수 있어 발표 문구 정리 필요
